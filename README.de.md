## Schnellstart-Workflow: So kalkulierst und verfolgst du mechanische Angebote

Befolge diese Schritte, um eine transparente Angebotsbaseline zu erzeugen.

### Schritt 1: Lege die kommerziellen Annahmen fest (definiere deine Margen)
**Aktion:** Öffne die Registerkarte `02_Assumptions`, um deine globalen Geschäftsparameter festzulegen.

Gib Projekt-ID, Projektname, Kundenname, Angebotsdatum, leitenden Kalkulator und Angebotsstatus ein. Diese **Projekt-ID** dient als Datenbankschlüssel, der deine Geschäftsdaten direkt mit deiner Mengenermittlung verknüpft.

## Warum ich diese Alternative zu Bau-Ausschreibungssoftware gebaut habe

Kommerzielle Kalkulation scheitert selten daran, dass ein Kalkulator Menge nicht mit Satz multiplizieren kann. Sie wird unzuverlässig, wenn **technische Fakten, kommerzielle Annahmen und finale Preisentscheidungen miteinander vermischt werden**.

Eine Menge kann aus einer Mengenermittlungssoftware stammen. Ein Materialsatz kann aus einem Lieferantenangebot stammen. Ein Arbeitskostensatz kann aus einer Standardgewerke-Annahme stammen. Gemeinkosten können in einer Formel eingebettet sein. Der Risikozuschlag kann manuell hinzugefügt werden. Der Aufschlag kann dann unmittelbar vor der Abgabe geändert werden.

Die finale Zahl kann immer noch vernünftig aussehen, aber die Begründung hinter der Zahl wird unprüfbar. Ich habe dieses Toolkit um eine einfache Trennregel herum gebaut:

> **Technische Fakten sollten einmal eingegeben werden. Kommerzielle Annahmen sollten zentral gesteuert werden. Die Bauberechnung muss reproduzierbar bleiben.**

Beispielsweise trägt eine Zeile wie `4" Copper Pipe Type L` ihre Projekt-ID, ihr Gewerk, ihre Einheit, ihre Menge, ihren Materialsatz, ihre Arbeitsstunden pro Einheit und ihren Geräte-/Subunternehmersatz als unleugbare technische Fakten. Die Engine verarbeitet dies dann zu direkten Materialkosten, direkten Arbeitskosten und direkten Gerätekosten, bevor sie sicher Gemeinkosten, Risikozuschlag und Aufschlag anwendet.

```text
MEP Quantity Takeoff
      ↓
Base Material / Labor / Equipment Cost
      ↓
Direct Construction Cost
      ↓
Operational Overhead
      ↓
Risk Contingency
      ↓
Commercial Markup
      ↓
Final Bid Submission
```

## Technische Details — Fortsetzung

<details>
<summary>Für technische Prüfer, Excel-Praktiker und Mitarbeiter</summary>

### Drei Fallen, die selbst erfahrene Kalkulatoren zu Fallen bringen

#### Falle 1 — Das finale Angebot als einzelne Zahl behandeln

**1. Eine Entscheidung wurde getroffen.**
Ein Angebot wird abgegeben, nachdem nur der finale Verkaufspreis und eine allgemeine erwartete Marge geprüft wurden.

**2. Die Entscheidung stützte sich auf eine unbemerkte Modellschwäche.**
Die Kalkulation trennte direkte Produktionskosten nicht klar von Gemeinkosten, Risikozuschlag und Aufschlag.

**3. Der Fehler verändert die Empfehlung.**
Ein Angebot kann wettbewerbsfähig erscheinen, weil die sichtbare Direktkostenzahl akzeptabel aussieht, während die kommerziellen Anpassungen zur Deckung der betrieblichen Gemeinkosten und der Projektunsicherheit fehlen, zu niedrig angesetzt oder inkonsistent angewendet werden.

**4. Warum die Begründung falsch ist.**
Der Verkaufspreis ist das Ergebnis mehrerer verschiedener ökonomischer Schichten. Diese Schichten als eine einzige Zahl zu behandeln macht es schwer zu bestimmen, ob eine Preisänderung auf Materialkosten, Arbeitskostenrisiko, Geräte-/Subunternehmerrisiko, Gemeinkostendeckung, Risikozuschlag oder angestrebte kommerzielle Rendite reagiert.

**5. Korrigierter Ansatz.**
Trenne die Berechnung in:

```text
Material Cost
+
Labor Cost
+
Equipment / Subcontract Cost
=
Direct Cost

Direct Cost
+
Overhead
+
Contingency
+
Markup
=
Final Bid
```

**6. Korrigiertes Entscheidungsergebnis.**
Der Kalkulator kann eine kommerzielle Annahme überarbeiten, ohne die Kalkulation neu aufzubauen. Ein Prüfer kann das finale Angebot außerdem bis zu den zugrunde liegenden Kostenkomponenten zurückverfolgen.

**7. Formel**

<details>
<summary>Berechnung der direkten Kosten und des finalen Angebots</summary>

```excel
Direct Material Cost
= Quantity × Material Unit Rate

Direct Labor Cost
= Quantity × Labor Hours / Unit × Applied Labor Rate

Direct Equipment Cost
= Quantity × Equipment Unit Rate

Direct Cost Subtotal
= Direct Material Cost
+ Direct Labor Cost
+ Direct Equipment Cost
```

Die Quellkonzeption definiert die Direktkosten-Zwischensumme als Berechnungsgrundlage für die anschließende Verteilung von Gemeinkosten, Risikozuschlag und Aufschlag. 

```excel
Overhead Allocation
= Direct Cost Subtotal
  × '02_Assumptions'!$B$5

Contingency Amount
= (Direct Cost Subtotal + Overhead Allocation)
  × '02_Assumptions'!$B$7

Markup Amount
= (Direct Cost Subtotal
  + Overhead Allocation
  + Contingency Amount)
  × '02_Assumptions'!$B$6

Line Item Final Bid
= Direct Cost Subtotal
+ Overhead Allocation
+ Contingency Amount
+ Markup Amount
```

</details>

---

#### Falle 2 — Einen Arbeitskostensatz ohne Kontrolle der Gewerkebeziehung verwenden

**1. Eine Entscheidung wurde getroffen.**
Eine Kalkulation wird als wettbewerbsfähig betrachtet, weil die Arbeitskomponente niedrig genug erscheint, um den Zielverkaufspreis zu stützen.

**2. Die Entscheidung stützte sich auf eine unbemerkte fehlerhafte Eingabe.**
Der auf eine Mengenermittlungszeile angewandte Arbeitskostensatz entspricht nicht konsistent dem Gewerk oder der Branche, die diese Zeile repräsentiert.

**3. Der Fehler verändert die Empfehlung.**
Ein Projekt mit Sanitärrohrleitungen, HVAC-Luftkanälen oder anderen spezialisierten Arbeiten kann mit einer generischen oder veralteten Arbeitsannahme kalkuliert werden. Die resultierenden direkten Arbeitskosten sind zu niedrig angesetzt, selbst wenn die Mengen- und Arbeitsstunden-pro-Einheit-Annahmen korrekt sind.

**4. Warum die Begründung falsch ist.**
Arbeitsmenge und Arbeitspreis sind verschiedene Dimensionen.

Eine korrekte Arbeitsstundenschätzung multipliziert mit einem falschen Stundensatz ergibt immer noch falsche Arbeitskosten.

**5. Korrigierter Ansatz.**
Behalte die Gewerk-zu-Satz-Beziehung im zentralen Annahmenbereich und leite den angewandten Arbeitskostensatz aus dem gewählten Gewerk/der gewählten Branche ab.

**6. Korrigiertes Entscheidungsergebnis.**
Die Kalkulation wird über Projekte hinweg konsistent, die dieselbe Kalkulationsrichtlinie verwenden. Wenn sich ein Standard-Arbeitskostensatz ändert, kann die Annahme zentral aktualisiert werden, statt einzelne Kalkulationen zu durchsuchen.

**7. Formel**

<details>
<summary>Gewerkebasierte Zuordnung des Arbeitskostensatzes</summary>

```excel
=MAP(
    B2:B1000,
    LAMBDA(
        trade,
        IF(
            trade="",
            "",
            XLOOKUP(
                trade,
                '02_Assumptions'!$B$11:$B$20,
                '02_Assumptions'!$C$11:$C$20,
                '02_Assumptions'!$C$11
            )
        )
    )
)
```

**Startzelle:** `H2`

**Arbeitsbereich:** `H2:H1000`

Die Quelle spezifiziert `Applied Labor Rate` als formelerzeugtes Feld und verwendet `MAP`, `LAMBDA` und `XLOOKUP`, um das Gewerk/die Branche der Mengenermittlung der Standard-Arbeitskostensatztabelle zuzuordnen. 

</details>

---

#### Falle 3 — Angebote als isolierte Kalkulationen statt als Pipeline verwalten

**1. Eine Entscheidung wurde getroffen.**
Das Management prüft einzelne Kalkulationen, wenn es wissen muss, wie viel Arbeit derzeit verfolgt wird.

**2. Die Entscheidung stützte sich auf einen unbemerkten Prozessfehler.**
Die Kalkulationsarbeitsmappe enthält den Angebotsbetrag, aber der Status nach der Kalkulation wird nicht konsistent konsolidiert.

**3. Der Fehler verändert die Empfehlung.**
Das Management weiß möglicherweise, dass mehrere Angebote erstellt wurden, ohne zu wissen, welcher Wert noch aussteht, welche Chancen gewonnen oder verloren wurden oder wie die gesamte Angebots-Pipeline aussieht.

**4. Warum die Begründung falsch ist.**
Eine Kalkulation beantwortet eine projektbezogene Preisfrage.

Ein Angebots-Tracker beantwortet eine portfoliobezogene kommerzielle Frage.

Das sind verschiedene Entscheidungen, die verschiedene Sichten auf dieselben Projekt-Stammdaten erfordern.

**5. Korrigierter Ansatz.**
Pflege den Projektstamm mit einem kontrollierten Angebotsstatusfeld:

```text
Draft
Submitted
Won
Lost
Pending
```

Verwende dann die projektbezogenen Kalkulationsausgaben und den Projektstatus als Grundlage für die Angebots-Tracking-Sicht.

**6. Korrigiertes Entscheidungsergebnis.**
Das Management kann übergehen von:

```text
"What is this project's estimate?"
```

zu:

```text
"What does the current estimating pipeline represent?"
```

Die Quellarchitektur definiert `07_Bid_Tracker` explizit als Angebots-Pipeline-Sicht für Projektangebotsbeträge, Beauftragungsstatus und Gewinnrateninformationen. 

**7. Formel**

<details>
<summary>Aggregationslogik der Pipeline</summary>

Die Implementierungsspezifikation etabliert den Tracker als Ausgabeschicht, die die Projekt- und Kalkulationsschichten konsumiert. Die exakte Arbeitsmappen-Formelimplementierung für jede Tracker-KPI ist im verfügbaren Quellmaterial nicht vollständig spezifiziert, daher sollte Folgendes als beabsichtigte Berechnungslogik und nicht als behauptete Quellformel behandelt werden:

```excel
Active / Open Bids
= COUNTIFS(Bid_Status_Range, "Submitted")
+ COUNTIFS(Bid_Status_Range, "Pending")
+ COUNTIFS(Bid_Status_Range, "Draft")
```

```excel
Won Value
= SUMIFS(
    Final_Bid_Range,
    Bid_Status_Range,
    "Won"
)
```

```excel
Win Rate
= IFERROR(
    Won_Count /
    (Won_Count + Lost_Count),
    0
)
```

Die Quelle bestätigt den Geschäftszweck des Trackers, stellt aber kein vollständiges zellenweises Formelwörterbuch für diese Ausgabe-KPIs bereit. 

</details>

### Beispielszenario

Betrachte ein kommerzielles Maschinenbauprojekt mit gemischtem Rohrleitungs- und Geräteumfang.

Die Mengenermittlung enthält:

| Eingabe               |                   Wert |
| ------------------- | ----------------------: |
| Project ID          |          `PRJ-2026-014` |
| Division / Trade    |       `Plumbing-Piping` |
| Item                | `4" Copper Pipe Type L` |
| Quantity            |              `1,200 LF` |
| Material Unit Rate  |           `$18.50 / LF` |
| Labor Hours / Unit  |          `0.12 hr / LF` |
| Applied Labor Rate  |           `$48.00 / hr` |
| Equipment Unit Rate |            `$1.50 / LF` |

Die Materialkomponente ist:

```text
1,200 × $18.50
= $22,200
```

Die Arbeitskomponente ist:

```text
1,200 × 0.12 × $48.00
= $6,912
```

Die Gerätekomponente ist:

```text
1,200 × $1.50
= $1,800
```

Die direkte Kostensumme wird daher:

```text
$22,200
+ $6,912
+ $1,800
= $30,912
```

Nimm an, die kommerziellen Annahmen sind:

| Parameter     | Satz |
| ------------- | ---: |
| Overhead      |  10% |
| Contingency   |   5% |
| Target Markup |  15% |

Gemeinkosten:

```text
$30,912 × 10%
= $3,091.20
```

Risikozuschlag:

```text
($30,912 + $3,091.20) × 5%
= $1,700.16
```

Aufschlag:

```text
($30,912 + $3,091.20 + $1,700.16) × 15%
= $5,355.50
```

Finales Angebot:

```text
$30,912.00
+ $3,091.20
+ $1,700.16
+ $5,355.50
= $41,058.86
```

Das nützliche Ergebnis ist nicht bloß die finale Zahl `$41,058.86`.

Die Kalkulation liefert nun eine nachvollziehbare Kostenstruktur:

| Kostenschicht       |         Betrag | Anteil am finalen Angebot |
| ---------------- | -------------: | -----------------: |
| Direct Material  |     $22,200.00 |             54.09% |
| Direct Labor     |      $6,912.00 |             16.84% |
| Direct Equipment |      $1,800.00 |              4.38% |
| Overhead         |      $3,091.20 |              7.53% |
| Contingency      |      $1,700.16 |              4.14% |
| Markup           |      $5,355.50 |             13.05% |
| **Final Bid**    | **$41,058.86** |        **100.00%** |

Das verändert das Prüfgespräch.

Statt zu fragen, ob `$41,058.86` „wettbewerbsfähig wirkt", kann der Kalkulator die tatsächlichen Kostentreiber identifizieren.

Das Projekt hat eine besonders große Materialkomponente. Arbeit ist die zweitgrößte direkte Kostenposition. Die Geräteexposition ist vergleichsweise kleiner. Die kommerziellen Anpassungen sind separat sichtbar.

Wenn sich das Materialangebot ändert, kann die Materialeingabe aktualisiert werden.

Wenn sich der Standard-Arbeitskostensatz ändert, kann der angewandte Arbeitskostensatz aus der Annahmentabelle aktualisiert werden.

Wenn sich die kommerzielle Richtlinie ändert, können Gemeinkosten, Risikozuschlag oder Aufschlag zentral geändert werden.

Die Berechnungskette bleibt dann:

```text
Project
   ↓
Quantity Takeoff
   ↓
Base Rates
   ↓
Direct Cost
   ↓
Commercial Adjustments
   ↓
Final Bid
   ↓
Bid Status
   ↓
Pipeline / Management View
```

Das ist die beabsichtigte Entscheidungsunterstützungsgrenze der Arbeitsmappe: **die Zahl einfacher zu erstellen, zu prüfen, zu überarbeiten und in die nächste kommerzielle Entscheidung zu übernehmen.**

```text
Division
Item Description
```

aus `04_Quantity_Takeoff`.

Die Quelle definiert `05_Estimate_Engine` als reine Berechnungsschicht und verbietet manuelle Eingaben im Berechnungsbereich. 

</details>

```excel
=IF(
    '04_Quantity_Takeoff'!A2:A1000="",
    "",

    * '04_Quantity_Takeoff'!F2:F1000
)
```

```text
Quantity × Material Unit Rate
```

Die Quelle spezifiziert `D2:D1000` als Füllbereich für diese Berechnung.

<details>
<summary>05_Estimate_Engine — Direkte Arbeitskosten</summary>

```excel
=IF(
    '04_Quantity_Takeoff'!A2:A1000="",
```

**Zweck:**

```text
Quantity
× Labor Hours / Unit
```

<details>
<summary>06_Bid_Summary — Aggregation auf Projektebene</summary>

`06_Bid_Summary` ist dafür konzipiert, die Kalkulation für eine gewählte `Project ID` zusammenzufassen.

Die Quelle etabliert den Geschäftszweck als:

* Auswahl eines Projekts;
* automatische Aggregation der Kostenstruktur;
* Offenlegung kommerzieller Kennzahlen;
* Darstellung der Kalkulation auf Projektebene statt zeilenweiser Prüfung.

Die exakten zellenweisen Formeln für das Zusammenfassungsblatt sind im verfügbaren Quellmaterial nicht vollständig spezifiziert. Daher stellt Folgendes das reproduzierbare Aggregationsmuster und keine behauptete Quellformel dar:

```excel
=SUMIFS(
    '05_Estimate_Engine'!$G:$G,
    '05_Estimate_Engine'!$A:$A,
    Selected_Project_ID
)
```

Dasselbe `SUMIFS`-Muster kann angewendet werden auf:

```text
Direct Material Cost
Direct Labor Cost
Direct Equipment Cost
Direct Cost Subtotal
Overhead Allocation
Contingency Amount
Markup Amount
Line Item Final Bid
```

Die Quellarchitektur bestätigt, dass `06_Bid_Summary` nachgelagert zur Projekt- und Kalkulationsschicht ist und Kosten nach gewählter Projekt-ID zusammenfassen soll. 

</details>

<details>
<summary>07_Bid_Tracker — Angebotslogik auf Portfolioebene</summary>

`07_Bid_Tracker` überführt das Modell von projektbezogener Kalkulation zu Pipeline-Verfolgung.

Die von der Quelle spezifizierten zugrunde liegenden Projektstatuswerte sind:

```text
Draft
Submitted
Won
Lost
Pending
```

Der Tracker kann das Kalkulationsportfolio daher strukturieren um:

* Projekt;
* Kunde;
* Angebotsdatum;
* Angebotsbetrag;
* aktuellen Status;
* beauftragten Wert;
* verlorene Chancen;
* Gewinnratenanalyse.

Die Quelle definiert den Tracker als automatisierte Sicht auf Projektangebotsbeträge, Beauftragungsstatus und Gewinnrate. 

Wo eine konkrete Implementierung erforderlich ist, ist das Standard-Excel-Aggregationsmuster:

```excel
Won Value
=SUMIFS(
    Final_Bid_Range,
    Bid_Status_Range,
    "Won"
)
```

```excel
Won Count
=COUNTIFS(
    Bid_Status_Range,
    "Won"
)
```

```excel
Lost Count
=COUNTIFS(
    Bid_Status_Range,
    "Lost"
)
```

```excel
Win Rate
=IFERROR(
    Won Count / (Won Count + Lost Count),
    0
)
```

Diese Formeln dokumentieren die beabsichtigte Geschäftsberechnung. Sie werden nicht als quell-extrahierte Zellenformeln dargestellt, wo die Quelle keine exakten Zellen spezifiziert.

</details>

<details>
<summary>08_Dashboard — Management-Sicht</summary>

`08_Dashboard` ist die finale Präsentationsschicht.

Die Quelle beschreibt dieses Blatt als Management-Cockpit zur Visualisierung von:

* aktiven Angeboten;
* Pipeline;
* Kostenzusammensetzung;
* angebotsbezogenen Managementinformationen.

Die Abhängigkeitsrichtung ist:

```text
03_Project_Setup
        +
05_Estimate_Engine
        ↓
08_Dashboard
```

Das Dashboard sollte daher bestehende Projekt- und Kalkulationsausgaben konsumieren, statt Kostenberechnungen unabhängig neu zu erzeugen.

Dies bewahrt eine einzige Berechnungsquelle und verhindert, dass die Managementebene zu einem zweiten, getrennten Kalkulationsmodell wird. 

</details>

### Validierungsregeln

| Feld                     | Regel                                                                              | Fehlerverhalten                                                                                         |
| ------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `Project ID`              | Muss den Projektstamm-Datensatz in `03_Project_Setup` identifizieren.                    | Nicht zugeordnete Projekt-IDs erzeugen gebrochene Projekt-zu-Mengenermittlung-Beziehungen und unzuverlässige Projektzusammenfassungen. |
| `Project Name`            | Wird als Projektstammdaten eingegeben.                                                   | Fehlender Name schwächt projektbezogene Berichte und Identifikation.                                       |
| `Client Name`             | Wird als Projektstammdaten eingegeben.                                                   | Fehlende Kundeninformationen schränken kundenbezogene Prüfung ein.                                 |
| `Bid Date`                | Verwende ein gültiges Datum im Format `YYYY-MM-DD`.                                          | Ungültige Daten gefährden Angebotsplanung und Periodenanalyse.                                           |
| `Estimator`               | Textfeld, das den verantwortlichen Kalkulator identifiziert.                                 | Fehlende Verantwortlichkeit schwächt die Prüfbarkeit.                               |
| `Bid Status`              | Verwende kontrollierte Werte: `Draft`, `Submitted`, `Won`, `Lost`, `Pending`.            | Nicht-Standardwerte brechen konsistente Pipeline-Gruppierung.                                                |
| `Division / Trade`        | Soll der Standard-Gewerkeliste entsprechen, wo ein Arbeitskostensatz-Nachschlagen erforderlich ist. | Nicht zugeordnete Werte können das Nachschlage-Rückfallverhalten auslösen.                                    |
| `Item Description`        | Erforderlicher beschreibender Mengenermittlungstext.                                                | Fehlende Beschreibungen reduzieren die Prüfbarkeit positionsweiser Kalkulationen.                                      |
| `Unit`                    | Gültige Kalkulationseinheit wie `LF`, `EA` oder `SQFT`.                              | Falsche Einheiten können die Menge/Satz-Beziehung entwerten.                                |
| `Quantity`                | Numerische gemessene Mengenermittlungsmenge.                                                | Leere oder ungültige Mengen verhindern sinnvolle Direktkostenberechnung.                                |
| `Material Unit Rate`      | Numerische Materialkostengrundlage.                                                      | Fehlende oder falsche Sätze verzerren direkte Materialkosten.                                               |
| `Labor Hours / Unit`      | Numerische Arbeitsaufwandsannahme.                                                      | Fehlende oder falsche Stunden verzerren direkte Arbeitskosten.                                                |
| `Applied Labor Rate`      | Formelerzeugt aus der zentralen Arbeitskostensatztabelle.                          | Unerwarteter Satz sollte eine Prüfung der Gewerk-zu-Satz-Zuordnung und der Annahmentabelle auslösen.             |
| `Equipment Unit Rate`     | Numerische Geräte- oder Subunternehmerkostengrundlage.                                             | Fehlende Werte erzeugen unvollständige Geräte-/Subunternehmerexposition. |
| `Overhead Rate`           | Prozentsatz, gepflegt in `02_Assumptions!B5`.                                     | Falscher Wert beeinflusst alle Kalkulationen, die den Parameter verwenden.                                             |
| `Target Markup`           | Prozentsatz, gepflegt in `02_Assumptions!B6`.                                     | Falscher Wert verändert die kommerzielle Verkaufspreisschicht.                                            |
| `Contingency Rate`        | Prozentsatz, gepflegt in `02_Assumptions!B7`.                                     | Falscher Wert verändert den Risikopuffer.                                                            |
| `Calculation Layer`       | `05_Estimate_Engine` sollte keine manuelle Eingabe enthalten.                             | Manuelle Überschreibungen gefährden die beabsichtigte Reproduzierbarkeit der Kalkulation.                              |
| `Currency Symbol`         | Zentral gepflegt in `02_Assumptions!B4`.                                      | Falsche Konfiguration beeinflusst die Darstellung, nicht die zugrunde liegende numerische Berechnung.           |
| `Formula Spill Area`      | Zielzellen müssen frei von manuellen Werten bleiben.                             | Blockiertes Dynamic-Array-Füllen erzeugt Excel-`#SPILL!`-Verhalten.                                         |
| `Assumption Cells`        | Kommerzielle Parameter müssen numerische Prozentsätze oder gültige konfigurierte Werte sein.     | Ungültige Annahmen propagieren falsche oder unbrauchbare Berechnungsergebnisse.                               |
| `Project-to-Takeoff Link` | Jede Mengenermittlungszeile sollte eine gültige Projekt-ID enthalten.                              | Verwaiste Mengenzeilen können nicht zuverlässig in projektbezogene Berichte einbezogen werden.                              |
| `Project Status`          | Status sollte innerhalb der kontrollierten Liste bleiben.                                  | Ungültige Statuswerte erzeugen inkonsistente Pipeline- und Gewinnratenanalysen.                              |

Das Quellkonzept unterscheidet ausdrücklich **manuelle Eingabebereiche, formelerzeugte Bereiche und Parameter-Steuerbereiche**, einschließlich der Konvention, dass blaue Zellen manuelle Eingaben darstellen, graue Zellen Formeln und gelbe Zellen Parametersteuerungen. 

### Implementierungshinweise

#### Dynamic-Array-Kompatibilität

Die Arbeitsmappe stützt sich auf moderne Excel-Funktionen, einschließlich:

```text
MAP
LAMBDA
XLOOKUP
IF
SUMIFS
```

Die Berechnungsarchitektur ist darauf ausgelegt, eine Formel einmal in der ersten Berechnungszeile einzugeben und sie über den Arbeitsbereich füllen zu lassen.

Dies ist eine bewusste Alternative zum manuellen Kopieren von Formeln durch jede Kalkulationszeile.

#### Disziplin der Berechnungsschicht

`05_Estimate_Engine` sollte rein rechnerisch bleiben.

Die beabsichtigte Grenze ist:

```text
Manual Fact
    ↓
Input Sheet
    ↓
Formula
    ↓
Calculation Output
    ↓
Summary
    ↓
Management View
```

Ein Benutzer sollte die berechneten direkten Kosten, die Gemeinkostenverteilung, den Risikozuschlag, den Aufschlag oder die finalen Angebotswerte nicht manuell bearbeiten.

#### Disziplin der kommerziellen Annahmen

Das folgende Muster wird absichtlich vermieden:

```excel
=G2*10%
```

wenn `10%` die konfigurierbare Gemeinkostenrichtlinie der Organisation repräsentiert.

Das bevorzugte Muster ist:

```excel
=G2*'02_Assumptions'!$B$5
```

Dieselbe Regel gilt für Zielaufschlag und Risikozuschlag.

Dies hält Geschäftsrichtlinie getrennt von Berechnungsmechanik.

#### Disziplin des Projektschlüssels

`Project ID` fungiert als Primärschlüssel.

Die Beziehung ist:

```text
03_Project_Setup
        │
        │ Project ID
        ▼
04_Quantity_Takeoff
        │
        │ Project ID
        ▼
05_Estimate_Engine
        │
        ├────────► 06_Bid_Summary
        ├────────► 07_Bid_Tracker
        └────────► 08_Dashboard
```

Dies ist die zentrale referenzielle Struktur der Arbeitsmappe.

#### Trennung von Fakten und Annahmen

Das Modell unterscheidet zwischen:

**Projekt- / technischen Fakten**

```text
Project ID
Division / Trade
Item Description
Unit
Quantity
Material Unit Rate
Labor Hours / Unit
Equipment Unit Rate
```

und:

**Kommerziellen Annahmen**

```text
Currency Symbol
Overhead Rate
Target Markup
Contingency Rate
Standard Labor Rates
Equipment Rates
```

Diese Unterscheidung ist zentral für die Reproduzierbarkeit.

Eine Änderung des Projektumfangs sollte die Projektdaten ändern.

Eine Änderung der Geschäftsrichtlinie sollte die Annahmen ändern.

Diese beiden Ereignisse sollten nicht dieselbe Wartungsaktion erfordern.

### Reproduzierbarkeits-Checkliste

Vor der Verwendung der Arbeitsmappe für ein reales Angebot verifiziere:

```text
[ ] Project ID exists in 03_Project_Setup
[ ] Project master fields are complete
[ ] Bid Status uses a controlled value
[ ] Division / Trade matches the standard trade list where applicable
[ ] Quantity values are numeric
[ ] Material rates are current
[ ] Labor-hours-per-unit assumptions are reviewed
[ ] Applied Labor Rate is being generated correctly
[ ] Equipment / subcontract rates are current
[ ] Overhead Rate is confirmed
[ ] Contingency Rate is confirmed
[ ] Target Markup is confirmed
[ ] No calculation cells have been manually overwritten
[ ] Dynamic-array spill areas are clear
[ ] 06_Bid_Summary reflects the intended Project ID
[ ] 07_Bid_Tracker reflects the current bid status
[ ] 08_Dashboard reflects the latest calculation state
```

Der Zweck dieser Checkliste ist nicht, Kalkulationsurteil zu ersetzen.

Sie soll verhindern, dass die Arbeitsmappe selbst zur Quelle vermeidbarer Kalkulationsinkonsistenz wird.

</details>
